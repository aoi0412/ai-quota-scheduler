# ai-quota-scheduler 設計書（2026-10-21）

- リポジトリ: `ai-quota-scheduler`（新規、harness2 とは別）。配置 `~/ghq/github.com/aoi0412/ai-quota-scheduler` 予定。

## 1. 目的・理由

- 問題: Claude サブスク 5時間枠・週間枠。昼 研究相談 → 上限到達 → 5時間待ち 発生。
- 一方 枠 余り → リセットで消滅 = 無駄。
- 目的: **ユーザー本人 利用 最優先**。本人 使い切れない分のみ harness2 に回す。
- 成功 = ①本人 待ち時間 ≤ W（15分）を守る ②リセット時点 残量 ≈ 0（5時間枠・週間枠 両方）。

## 2. ゴール / 非ゴール / アンチゴール

ゴール
- 残量 + リセット時刻 定期観測。
- 2階層 MPC で harness 並列数 決定。
- 本人 使用量 予測（時間帯・曜日別、過去ログ学習）。
- harness2 タスク → ジョブキュー投入 → 余り枠で順次実行。
- 窓口サブエージェント（Claude Code）からキュー操作・状況確認。

非ゴール
- Gemini 対応（残量 観測不可 → 当面 対象外）。
- Codex 対応は任意（解約予定。アダプタ枠のみ用意、実装後回し）。
- harness2 アルゴリズム自体 改良。
- GUI / Web ダッシュボード。

アンチゴール（技術的に動いても失敗扱い）
- 本人 利用時 harness 起因で上限到達 → 待ち > W 発生。
- 週の途中 本人 週間枠 到達。
- 予測ミス時 harness 側 減速せず 走り続ける。
- 観測不能時（API 失敗等）に harness 走り続ける。

## 3. 制約

- 実行環境: 自宅 常時稼働 Linux デスクトップ。systemd 常駐。
- 言語 Python 3.12 + uv。
- 枠 = アカウント全体共有。本人 Mac / claude.ai 利用分も同じ枠 消費。
- 観測 粒度粗い（% 単位）、遅延あり。
- harness 操作 粗い: rollout 途中停止 困難 → 操作量 = 並列数（0..k）+ 次ジョブ開始可否。
- harness2 実行役 現状 OpenCode / Codex のみ → Claude 枠 消費には Claude Code 実行役 追加 必要。

## 4. 決定事項（ユーザー合意）

### 4.1 観測（アダプタ方式）
- プラットフォーム毎 アダプタ: `read() -> {window: {used_pct, resets_at}}`、`launch(job)`。
- Claude（主対象）:
  - 第一候補: 使用量 API 定期ポーリング（ccusage 同方式、非公開 → 変更リスク明記、失敗時 安全側停止）。
  - 補助: Claude Code statusline JSON。
    - 項目 `rate_limits.five_hour / seven_day`。
    - 各窓 `used_percentage`, `resets_at`。
- Codex（任意）: `~/.codex/sessions/**/*.jsonl` 内。
  - 項目 `rate_limits.primary/secondary`。
  - 各窓 `used_percent`, `window_minutes`, `resets_at`。
  - 値 = 最後に使った時点のもの → 鮮度 注意。
- Gemini: 観測しない。

### 4.2 外乱（本人 使用量）推定・予測
- 観測可能 = 合計 使用率のみ。
- harness 自己消費 = `claude -p` 出力 トークン数 → %換算係数 オンライン学習。
- 本人 使用量 d = Δ合計% − Δharness推定%。
- 予測: 時間帯 × 曜日 別 分布、過去ログ学習。評価は平均でなく **上側分位点（90〜95%）**。
- コールドスタート: データ不足期間 = 記録のみ or 保守的運用（並列数 最小）。

### 4.3 制御（2階層 MPC、後退ホライズン）
- 再計画周期: 数分（例 5分）。毎回 最初の一手のみ実行。
- 上位（週間）:
  - ホライズン = 週間リセットまで。
  - 目標 = リセット時 残量 ≈ 0。
  - 制約 = 残り期間 本人 予測使用量（上側分位）常時確保。
  - 出力 = 各5時間ブロック harness 予算。
- 下位（5時間）:
  - ホライズン = 5時間リセットまで。
  - 目標 = 上位予算内で 使い切り。
  - 制約 = 本人 待ち時間 ≤ W = **15分**（設定可）。
  - 基本条件の特殊ケース: 本人使用0・全開/停止2値 → `T − R/r ≤ W`（T=リセットまで, R=残量, r=harness消費速度）。
  - 操作量 = 並列数 0..k。離散 → 総当たりで解く。
- r（harness 消費速度）: 固定値でなく 直近実測から更新。初期値 控えめ。
- 本人 使用 急増 → 次周期で即 減速/停止。

### 4.4 実行
- ジョブキュー: 中身不問。harness2 実行単位（ベンチ1タスク、自作タスク等）なら何でも。
- ジョブ単位（ユーザー確定）= harness2 の1回の実行（rollout → 改善 → rollout のループ全体）。
  - harness2 スケジューラ（`core/schedule.py` 周辺）に外部制御口を追加: 一時停止 / 再開 / 並列数変更。
  - 制御器 → 制御口 経由で絞る・止める。最適化ループ本体は改造しない。
- 実行役: 制御器指示に従い キューから取得 → Claude Code（`claude -p`）経由で harness2 実行。
- 停止要求 → 新規 rollout 開始せず 区切りで停止。
- harness2 改造: **Claude Code substrate 新規追加（ユーザー確定）**。
  - 最適化対象 = Claude Code 構成一式（CLAUDE.md、skills、subagents、hooks、tool guidance 等）を harness2 の 8要素に対応付け。
  - 理由: Claude サブスク枠 = 公式クライアント専用 → OpenCode 経由不可。
  - 副産物: 採用された harness → 本人の Claude Code 環境へ取り込み可能。
  - trajectory 読取（`read_trajectory()`）は `claude -p --output-format stream-json` 等から新規実装。
- モデル呼び出し役の課金枠（ユーザー確定）:
  - 実行役 = サブスク枠（Claude Code）。
  - 改善役 = サブスク枠。既存 `claude_cli` の Vertex 固定（`CLAUDE_CODE_USE_VERTEX=1`）を外す認証モード追加。
  - judge = ベンチ実行時のみ任意。API キー別枠。制御器の予算計算 対象外。

### 4.5 窓口
- 専用サブエージェント（Claude Code）= 人間向け窓口。キュー投入・状況確認（「今週どれだけ回った？」等）。
- 常時動作部分 = 常駐プロセス。サブエージェントは制御ループ本体ではない。

### 4.6 解釈・判断（レビュー反映）
- W の意味（ユーザー回答由来）: 本人 上限到達は許容。ただし到達からリセットまで ≤ 15分。
- 実行中 rollout の最悪消費 → harness 予算側で確保（本人側の余裕から引かない）。【私の判断】
- 週間枠: 本人 予測使用量 上側分位点 = ハード制約。harness 側のリスク取り 不可。
- モデル別上限（Opus 週間枠等）: API に出る全窓を追跡・制約化。harness は本人主用モデルと別系統（例 Sonnet 系）優先。【私の判断】
- 使用量の帰属: harness 専用 `CLAUDE_CONFIG_DIR` 分離。本人 対話セッションと混ぜない。【私の判断】
- コールドスタート: 最初1週間 記録のみ → 以降 並列1から開始。【私の判断】

## 5. ビルダー裁量

- 使用量 API の具体的エンドポイント・認証の扱い（調査して決定、非公開である旨 ドキュメント化）。
- 予測モデル具体形（経験分位点、指数平滑、等）。
- 状態保存形式（SQLite 等）、ジョブキュー実装。
- 常駐プロセス ↔ サブエージェント間 IF（CLI、ローカルソケット等）。
- 並列上限 k、再計画周期、r 初期値、分位点 既定値。
- harness2 Claude Code substrate 実装詳細。
- ログ・メトリクス形式。

## 6. 安全策（必須）

- 観測失敗・データ古い → harness 停止（安全側）。
- 429 / 上限到達 検知 → 即停止。
- 手動キルスイッチ。
- 判断根拠（観測値・予測・決定）毎周期 記録 → 事後検証可能。
